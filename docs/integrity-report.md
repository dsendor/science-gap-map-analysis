## The brief's five known holes, checked

**1. No `rank` field, though the site sorts by rank.** Confirmed. No gap or capability record carries a rank, ordering or priority key. Whatever backs the site's rank sort is not in the export, so rank cannot be reconstructed and is not something this augmentation touches.

**2. `tags` has no documented enum.** Confirmed — no enum is declared in `schema.json`. Observed values:

- On gaps: `Security Risk` (1), `Safety Risk` (1)
- On capabilities: `Security Risk` (26), `Governance/Ethics Risk` (19), `Safety Risk` (18), `Longevity and Aging` (5), `Brain-Body Interactions` (2), `Origin of Life` (2), `Recycling` (2)

Only 2 tag assignments exist across all 103 gaps, so gap tags carry almost no signal. The risk vocabulary the brief expects — safety, security, governance/ethics — does appear, but almost entirely on capabilities.

**3. Resource `types` has no documented enum.** Partly refuted. `schema.json` declares none, but `gapmap-data.json` carries an undocumented top-level `resourceTypes` array — 11 values — that neither the README nor the schema mentions. Observed usage:

**4. No per-record timestamps or version numbers.** Confirmed. The only temporal marker is the export-level `exportDate`. Change over time cannot be measured from this export alone, which is why `data/baseline/2026-07-29/` is committed verbatim and hash-pinned: it is the only way a future export can be diffed against this state.

**5. Nothing marks a capability as necessary, sufficient, or partial for its linked gap.** Confirmed. Edges are untyped — a capability that would fully close a gap and one that nibbles at it are indistinguishable in the data. This is the single most consequential absence for anyone trying to reason about what actually unblocks what, and it is why the critical-path work in Phase 5 has to reconstruct link semantics by hand.

## Additional findings not in the brief

### The bipartite graph is only half-populated

`schema.json` documents `capabilities[].gaps` as "IDs of R&D gaps addressed by this capability". In this export **that array is empty for all 369 capabilities** (0 populated). All 389 edges exist solely on the gap side, in `gaps[].foundationalCapabilities`.

Consequences for a consumer: the graph is still complete, because the gap side carries every edge, but any code that trusts the documented capability-side field builds an empty graph and silently reports that no capability addresses any gap. Anyone starting from `capabilities.json` alone gets nothing. This is a straightforward export bug and probably the most useful single thing to tell them.

### Two capabilities have no description

- `1cfcb37e-2a00-80a2-a53c-f8602d0a4f8c` — Earthquake Prediction
- `1cfcb37e-2a00-80c8-9a7d-deb9ed5cef96` — Subduction Zone Observation

`description` is listed as required in their own `schema.json`, so these two records fail their own schema.

### Orphans

- 3 capabilities carry no resources at all.
- Every gap has at least one capability, and every gap has a field. No dangling references in any direction.
